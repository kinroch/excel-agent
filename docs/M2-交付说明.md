## 1. 计划与实际的偏差说明

实施方案的 M2 范围为「F1~F8、解析引擎、预览与字段说明、工作台三区块」。实际交付与范围的差异如下，其中 1~3 项属**实现决策**（下文第 5 章逐条给理由），4 项属**遗留待确认**（第 7 章）：

1. **新增 `tools/fixtures/make_e2e_fixture.py`**——实施方案未规划端到端样本生成器。但 M2 的验收对象是「解析引擎 + 前端渲染 + 异步轮询」三者的组合行为，样本必须**确定性且可人工复核**（预期值写死在样本生成器的 docstring 里），否则 E2E 断言无从写起。该脚本同时可作手工验收的样本源。
2. **多级表头判据拆为「严格 / 宽松」两套**——技术文档只要求「多级表头按上级/下级拼接」。实现中发现：若复用同一套严格判据（要求取值互不重复），被合并的上级组名展开后必然重复，**真实的多级表头永远识别不出来**。故新增宽松判据 `_looks_like_upper_header`，并补两条区分判据把「整行合并的大标题」与「真正的上级表头」分开（详见第 5 章 ③）。
3. **合并单元格改由直接解析 OOXML 包获取**——技术文档未指定实现路径。openpyxl 3.1.5 的**只读模式工作表完全没有 `merged_cells` 属性**（实测 `hasattr` 为 `False`），原实现恒返回空集。改为流式解析 `xl/workbook.xml` + `xl/_rels/workbook.xml.rels` + `xl/worksheets/sheetN.xml` 的 `<mergeCells>`（详见第 6 章 缺陷 1）。
4. **解析产物落 CSV 副本**——技术文档未明确「预览数据从哪读」。实现选择把规整后的数据落成 `uploads/_parsed/{file_id}/sheet_{i}.csv`，让 F7 预览与 M3 分析沙箱**共用同一份数据**（详见第 5 章 ①）。

> **对已冻结基线文档的改动：无。** `db/schema.sql` 逐字未动，13 张表 / 21 个索引与数据库设计文档 V1.0.2 第 5 章完全一致（门禁实测见第 8 章）。

## 5. 关键设计决策（评审重点）

### ① 解析产物落 CSV 副本，预览与分析共用同一份数据

`uploads/_parsed/{file_id}/sheet_{i}.csv`。

- **问题**：F7 预览需要一个稳定的读取源；M3 分析沙箱也需要一份规整后的数据。若各自读原件、各自解析，会埋下「预览所见 ≠ 分析所得」的隐患。
- **决策**：解析时一次性把「补齐列宽 → 展开合并 → 剔除空行列 → 切出数据区」的结果写成 UTF-8 CSV，F7 与 M3 都只读这份副本。
- **路径可推导**：由 `file_id + sheet_index` 直接算出，**无需新增数据库列**，因此 `db/schema.sql` 保持冻结。
- **代价与兜底**：副本属可再生成的派生产物；`remove_parsed_dir` 在每次重新解析前清空旧产物（否则上一次的 `sheet_2.csv` 残留会被误读）；副本缺失时 `read_preview` 抛「解析产物已被清理，请重新上传文件」。

### ② 上传走「202 + 后台线程」，且后台任务必须自建数据库会话

- F1 受理后立即返回 202（`parse_status = "parsing"`），解析交给 `BackgroundTasks` + `asyncio.to_thread`。
- 理由：解析是阻塞型 IO/CPU 任务，放在请求内会把响应时间与文件大小绑定，大文件直接超时（NFR-P2）。
- **关键约束**：`BackgroundTasks` 在响应发出**之后**执行，此时请求级数据库会话已关闭 → `_parse_worker_sync` **必须自建 `SessionLocal()`**。这是本模块最容易踩的坑，已写入代码注释。
- 进度按 Sheet 粒度短事务 commit（5%~95% 映射），避免长事务阻塞其它请求。

### ③ 多级表头判据必须分成「严格 / 宽松」两套

- `_looks_like_header`（严格）：填充率高 + 全文本 + **取值互不重复** → 用于定位下级表头行。
- `_looks_like_upper_header`（宽松）：填充率高 + 全文本（**不要求互不重复**）→ 用于识别上级表头行。
- **为什么必须分开**：上级表头的组名是合并单元格，展开后必然连续重复（如「销售维度」跨 2 列）；若用严格判据，真实的多级表头永远识别不出来。
- 再加两条区分判据把「整行合并的大标题」与真正的上级表头分开：① 上级行去重后取值数 ≥ 2（大标题展开后全行同值，去重只有 1 个）；② 上级行与表头行取值集合不同。
- 已知取舍：若上级只有唯一一组名称（覆盖全部列），会被判为大标题而丢弃，此时仅用下级列名。这是极少见的形态，信息损失很小。

### ④ 前端轮询只在「解析进行中」开启

- F3 详情：`refetchInterval` 由响应中的 `parse_status` 决定（`parsing`/`pending` → 800ms，终态 → `false`）。
- F2 列表：解析条件是「任一子项在解析」，无法从单个 query 的 data 简洁表达，故用 `useEffect` + `setInterval` 驱动；**依赖取 `refetch` 函数引用而非整个 query 对象** —— 否则每次渲染都会重建定时器，轮询将无法按 800ms 稳定触发。
- 若不这样做，文件全部解析完成后仍会每 800ms 发一次请求，形成「后台空转」。

### ⑤ `_load_owned_file` 把三种情况统一为 2005

「不存在」「已删除」「非本人」一律返回 2005（同样的状态码与文案）。若分别返回不同错误，攻击者可用 file_id 枚举探测他人文件是否存在。

### ⑥ 缺失值策略「只记录口径，不改写数据」

`files.missing_policy` 只存策略枚举；填充/剔除延迟到 M3 分析期，作用于**送进沙箱的数据副本**。因此策略可以随时来回切换而不产生不可逆影响 —— 这也是 E2E C9 敢做「提示 → 剔除 → 提示」往返断言的前提。

### ⑦ 解析处理信息行用纯函数复现，不新增数据库列

F5 的「解析处理」文案由 `build_sheet_note()` 生成，其**全部入参都被持久化到 `quality_json.sheet_meta`**。因此 F5 可以用同一函数原样复现该文案，无需新增列（`data_sheets` 表保持冻结）。

### ⑧ 删除 = 软删记录 + 硬删数据

`files.deleted_at` 打标（列表按此过滤），同时硬删原件、CSV 产物与 `data_sheets` 明细。理由：解析产物是可再生的派生数据，硬删可避免磁盘无界增长；记录软删保留了审计线索。

### ⑨ CSV 编码探测：BOM 优先 → 按候选顺序取第一个 strict 可解者

详见第 6 章 缺陷 2 —— 这里曾是本模块最严重的一个系统性缺陷，实现方式已因此改写。

## 6. 缺陷修复记录

> 以下 4 项均为 M2 实施过程中定位并修复的真实缺陷。第 1~3 项**无法被静态检查或接口级测试发现**，只有真实浏览器/真实样本才会暴露 —— 这也是坚持为每个里程碑编写 E2E 的直接理由。

### 缺陷 1：合并单元格数量恒为 0（`merged_cells = 0`）

| 项 | 内容 |
| --- | --- |
| 现象 | 含 4 个合并区域的样本文件，F5 的解析处理信息行不出现「合并单元格已向下填充展开」，质量小结「合并单元格」恒为 0 |
| 根因 | `openpyxl` 3.1.5 的 `ReadOnlyWorksheet` **完全没有 `merged_cells` 属性**（实测 `hasattr(ws, "merged_cells")` 为 `False`）。原实现用 `getattr` 取该属性并默认空列表，因此静默失效、不报错 |
| 修复 | 新增 `read_merged_ranges(path)`，直接流式解析 OOXML 包内 `xl/workbook.xml` + `xl/_rels/workbook.xml.rels` + `xl/worksheets/sheetN.xml` 的 `<mergeCells>`，用 `ET.iterparse` 保持内存占用恒定 |
| 验证 | `test_f5_multi_sheet_and_notes` 断言 `merged_cells = 4`；E2E C4 / C8 |

### 缺陷 2：UTF-8 中文 CSV 被系统性误判为 GB18030（数据乱码）

| 项 | 内容 |
| --- | --- |
| 现象 | 一个正常的 UTF-8 中文 CSV，解析后中文变乱码（`部门` → `閮ㄩ棬`） |
| 根因 | 原实现按「解出的中文字符数最多」打分选编码。但 GB18030 每 **2 字节**产 1 个汉字、UTF-8 每 **3 字节**产 1 个汉字 —— 同一段字节用 GB18030 解出的汉字数**总是更多**，该打分函数在中文文本上必然选中 GB18030 |
| 修复 | 改为「BOM 优先 → 按候选顺序（UTF-8 → GB18030 → Big5）取第一个 strict 可解者」。严格 UTF-8 解码器对非法字节序列**必然报错**，因此顺序优先即可正确判定；`_try_decode` 仅在 `exc.reason == "unexpected end of data"` 时截断重试（`invalid start byte` 直接返回 `None`，不做容错） |
| 验证 | 新增回归用例 `test_csv_utf8_chinese_not_misdetected`；E2E C10（GBK → GB18030 与 UTF-8 两条路径都覆盖） |

### 缺陷 3：【高】浏览器端文件上传 100% 失败

| 项 | 内容 |
| --- | --- |
| 现象 | 在真实浏览器里上传任何文件，后端返回 400 `{"code":9000,"message":"参数错误[body.file]：Field required"}`；而同一份文件用脚本直连接口上传则完全正常（202 + 解析成功） |
| 根因 | `client.ts` 的 axios 实例设了全局默认头 `Content-Type: application/json`。axios 1.x 的 `defaults.transformRequest` 中有一条判据：<br>`isFormData(data) ? (hasJSONContentType ? JSON.stringify(formDataToJSON(data)) : data) : ...`<br>其中 `hasJSONContentType` 取自**请求头**。于是上传时塞进去的 `FormData` 被先送进 `formDataToJSON` —— 该函数只处理字符串/数组，**直接丢弃 File / Blob** —— 最终发出的请求体是空对象 `{}` |
| 误导性 | 网络面板里请求确实发出去了、方法确实是 POST、HTTP 也连通，唯独文件永远传不过去。且**接口级测试与 TypeScript 类型检查都覆盖不到**（pytest 里是 TestClient 直接调函数，tsc 只看类型） |
| 修复 | `client.ts` 移除实例级 `Content-Type` 默认头。不设默认头**不影响 JSON 接口**：axios 的 `transformRequest` 遇到普通对象时会自动补 `application/json`；`FormData` 则原样透传，交由浏览器写入带 `boundary` 的 `multipart/form-data` |
| 验证 | E2E C3 起全部通过；同时**回归 M1 E2E**（31 项断言全过），确认 A1/A2 的 JSON 请求未受影响 |

### 缺陷 4：M1 遗留的偶发失败用例 `test_tampered_signature_is_rejected`

| 项 | 内容 |
| --- | --- |
| 现象 | 连跑 3 轮 M1 测试出现 1 次失败：`Failed: DID NOT RAISE <class 'BizError'>` |
| 根因 | 该用例通过「改动签名段**最后一个字符**」来伪造令牌。但 HS256 的签名是 32 字节 HMAC，base64url 无填充编码后是 **43 个字符**：42 个字符承载 252 比特，第 43 个字符只用**高 4 位**承载剩余 4 比特，低 2 位是填充位。因此只要改动后高 4 位不变，解码出的字节**完全一致**，签名依然有效 |
| 修复 | 改为篡改**首个字符**（6 个比特全部有效，解码结果必然不同），并在 docstring 中写明填充位原理，避免后人再改回末位 |
| 验证 | 单用例连跑 10 轮全绿；完整套件连跑 5 轮全绿（62 passed × 5） |

**已排除的假缺陷（记录以免重复排查）**：E2E 首次运行时样本 CSV 报「已忽略 11 个全空行」。经查是**样本生成器自身的问题** —— `Path.write_text` 以文本模式打开文件，在 Windows 上会把 `\n` 再次翻译成 `\r\n`，使原本的 `\r\n` 变成 `\r\r\n`，被 `csv.reader` 视作「每行后跟一个空行」。解析器行为正确，改用 `write_bytes` 后消失。
