## 1. 计划与实际的偏差说明

实施方案的 M1 范围为「A1~A4、JWT、角色依赖、双端登录页与守卫」。实际交付与该范围的差异有二，均已在下文「待确认项」登记：

1. **新增 2 个错误码（1005 账号格式 / 1006 登录限流）**——技术文档 5.1 与 5.4 分别要求「账号需为手机号或邮箱格式校验」与「登录接口按 IP + 账号 5 次/分钟限流」，但**附录 A 错误码全表未给出对应码**。为保证前端能区分「可内联修正的表单错误」与「系统异常」，按附录 A 自身的段规划（1000~1099 = 认证与权限）在**段内补码**，属补齐缺口而非另造错误码。
2. **ORM 模型独立为 `app/infra/models.py`**——技术文档 3.1 的目录树把「ORM 模型」列在 `infra/db.py` 内。M0 已将 db.py 定为「连接 + 生命周期」，再容纳 13 张表的映射会使其膨胀至 500+ 行。拆出后**仍在 infra 层内，依赖方向不变**。

## 4. 代码评审结论（自查）

### 4.1 评审发现并已修复的真实缺陷（4 项）

| # | 缺陷 | 影响 | 发现方式 | 修复 |
| --- | --- | --- | --- | --- |
| ① | `detectSide()` 用 `pathname.startsWith('/admin')` 判端 | 管理端应用内路由为 `/dashboard`、`/users`、`/sessions`（**都不以 /admin 开头**），导致管理端的 401 会清除**用户端**登录态并跳到用户端登录页 | 阅读 UI/UX 3.4 路由表与代码交叉核对 | 由入口文件调用 `setApiSide()` 显式声明，路径推断降级为兜底 |
| ② | 401 拦截器拦截 `/auth/login` 的失败响应 | 附录 A 1003 的 HTTP 状态正是 401，拦截器会把登录页刷新掉 → **「账号或密码错误」永远无法显示**，直接破坏 AC-4.1-3 | 浏览器 E2E C9 | 公开认证接口（A1/A2）的 401 不触发跳转，透传给表单 |
| ③ | 守卫只看本端登录态 | 普通用户在用户端登录后访问 admin.html 时，管理端键本就为空 → 被判「未登录」（`?from=admin`），而 UI/UX 3.2 要求 `?denied=1` 与「无权限访问管理后台」 | 浏览器 E2E C4 | 守卫改为同时读取两端登录态：任一端有令牌即视为已登录，再按**持有令牌那一端**的角色判越权 |
| ④ | 非 2xx 响应的业务文案全部丢失 | 后端在 HTTP 400/401/403/429 的响应体中携带了正确文案，但拦截器直接抛 `AxiosError`，页面只显示「网络异常（Request failed with status code 401）」→ **附录 A 的全部业务提示到不了用户眼前** | 浏览器 E2E C9 | 只要能解析出业务码，一律转换为 `BizApiError(code, message)` 再抛出 |

> 缺陷 ②③④ **均无法被静态检查或后端接口测试发现**，是引入真实浏览器 E2E 后才暴露的。这也是把 `tools/e2e_m1_auth.mjs` 保留为常规验证手段的原因。

### 4.2 关键设计决策（供评审重点核查）

1. **为什么用 `bcrypt_sha256` 而非裸 `bcrypt`**
   裸 bcrypt 只取前 **72 字节**，超出部分被静默忽略。本系统账号为手机号/邮箱、密码允许中文（一个汉字 UTF-8 占 3 字节），用户设置 25 个汉字即超过 72 字节 → 出现「不同密码也能登录」。`bcrypt_sha256` 先用 SHA-256 压缩为定长摘要再交给 bcrypt，从根本上消除截断风险。
   → 证据：`test_bcrypt_sha256_prevents_72_byte_truncation` 断言「仅尾部不同的超长中文密码必须被拒绝」。

2. **为什么 jti 黑名单是内存级**
   本期单进程 uvicorn 部署，进程内字典即可覆盖登出。代价已明确记录：**多进程/多实例部署时黑名单不跨进程共享**（见「待确认项」）。存储结构为 `jti -> 过期时间戳`（而非集合），以支持惰性清理，防止内存无界增长。

3. **为什么每个请求都查库校验用户存在性与状态**
   令牌签发后无法撤回，若仅信任载荷中的 `role`，管理员停用某账号后在令牌过期前（最长 7 天）该账号仍可访问，且「降权后旧令牌仍具管理员权限」。查库使**停用即时生效**，本地 SQLite 单表主键查询成本极低。
   → 证据：`test_token_becomes_invalid_after_account_disabled`

4. **限流口径为「只统计失败 + 成功清零」**
   技术文档 5.1 原文为「登录接口按 IP + 账号 5 次/分钟」。若把成功请求也计入，用户在「登录 → 登出 → 再登录」的连续操作中会被莫名拦截（误伤）；只统计失败更贴合「防爆破」这一既定目的。
   → 证据：`test_successful_login_resets_failure_counter`

5. **`get_current_claims`（不查库）与 `get_current_user`（查库）分离**
   登出在语义上**应当总是成功**——即使账号刚被停用，也应允许调用方清理登录态，故 A3 走轻量依赖；其余业务路由走查库依赖以获得最新状态。

6. **注册接口恒将 role 置为 `user`**
   技术文档 5.4 与 UI/UX 6.2 均明确「管理员账号不开放自助注册」，管理员只能由 `scripts/init_admin.py` 创建。该脚本自身也设防：拒绝覆盖已存在的普通用户（需显式 `--promote`）、拒绝在未传 `--reset-password` 时改已存在管理员的密码（避免重复执行脚本误改线上密码）。

## 5. 待确认项与已知限制

| # | 事项 | 说明与建议 |
| --- | --- | --- |
| 1 | **错误码 1005 / 1006 需回写文档** | 附录 A 未覆盖「账号格式非法」与「登录限流」。本次按 1000 段规划段内补码。建议在下次文档修订时把两项补入附录 A；若评审要求严格对齐原始全表，回退成本极小（改动 `errors.py` 与 2 处 `raise`） |
| 2 | **ORM 模型位置** | `app/infra/models.py`（技术文档 3.1 原列在 `infra/db.py` 内）。如需严格对齐文档目录树，可合并回 db.py（仍在 infra 层内，依赖方向不变） |
| 3 | **`/sessions` 路由两端重叠（M0 遗留）** | 用户端与管理端均定义 `/sessions`（UI/UX 3.4），Nginx 无法按路径区分两端。已在 `deploy/nginx.conf.example` 标注，建议 M6 前确认是否改为 `/admin/sessions`（需同步修订 UI/UX 3.4）。**M1 实测确认：该重叠暂不影响认证链路**（两端为独立 HTML 外壳页，登录态键已隔离） |
| 4 | **登录限流与令牌黑名单的失效面** | 二者均为**内存级**，多进程 / 多实例部署时需替换为 Redis（限流用 ZSET 滑窗，黑名单用带 TTL 的键）或 Nginx `limit_req` + 数据库 `token_version` 字段。触发条件：部署形态从单进程变为多进程 |
| 5 | **`X-Forwarded-For` 的可信边界** | 真实 IP 取 XFF 最左段（经 Nginx 反代场景）。直接公网暴露后端时 XFF 可被伪造从而绕过 IP 维度限流。当前部署形态后端仅监听 127.0.0.1（`deploy/eda-backend.service`），不存在该暴露面；若改为公网直连需引入可信代理白名单 |
| 6 | **管理端登录入口的角色约束为「前端前瞻 + 后端二次校验」** | 技术文档 5.4 明确 A2 双端共用、由前端守卫拦截；本次实现为「前端在登录响应后校验 role，不符则**主动吊销刚签发的令牌**并提示」。若评审认为应在后端按入口参数硬拦截，需新增请求字段（属接口契约变更） |
| 7 | **浏览器 E2E 尚未纳入 CI** | `tools/e2e_m1_auth.mjs` 需先拉起前后端服务，CI 中需增加服务编排步骤。当前作为**本地/评审前的手工验证手段**，建议在 M7「合规加固与联调」时纳入流水线 |
